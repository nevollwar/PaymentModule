## 2. Теоретические основы

Контрактное программирование рассматривает взаимодействие программных модулей как юридический контракт между *клиентом* (вызывающей стороной) и *сервером* (вызываемым методом):

$$\{P\} \quad S \quad \{Q\}$$

где:
- **$P$ (Precondition / Предусловие):** Обязательство вызывающей стороны. Условие, истинность которого клиент обязан гарантировать непосредственно перед вызовом метода $S$.
- **$S$ (Statement / Тело операции):** Алгоритм выполнения функции/транзакции.
- **$Q$ (Postcondition / Постусловие):** Обязательство исполнителя. Состояние, гарантируемое методом $S$ после его штатного завершения, при условии истинности $P$.
- **$I$ (Invariant / Инвариант):** Предикат, определяющий допустимое согласованное состояние сущности. Инвариант истинен до вызова публичного метода и обязан сохраняться после его завершения.

### Принцип разделения контроля контрактов в проекте:
1. **Детерминированный UI-мониторинг:** реализация *чистых функций* (pure functions) вида `Find*PreViolation(...)`, выполняющих бессимптомную проверку предикатов предусловий без побочных эффектов (*Side Effects*). Служит для реактивного управления свойствами интерфейса (`IsPreValid`, `CanExecute`).
2. **Доменные защитные барьеры (*Guards*):** класс `Guard.Requires(bool condition, string message)`, гарантирующий fail-fast семантику в ядре системы. При $P = \text{false}$ выбрасывается строго типизированное исключение `PreconditionException`.
3. **Апостериорный аудит постусловий:** предикатная проверка состояния после выполнения транзакции через `Debug.Assert(...)` и упаковку результатов в структуры аудита (`DepositResult`, `TransferResult`, `ServicePaymentResult`).

## 4. Формальная спецификация и реализация операций

### 4.1. Операция 1: Перевод со счёта на счёт (`Bank.Transfer`)

* **Сигнатура:** `TransferResult Transfer(Account from, Account to, decimal amount)`
* **Инвариант агрегата:** $\sum_{a \in Accounts} a.Balance = \text{const}$

#### Формальная спецификация:
* **Pre ($P$):**
  $$from \neq \text{null} \ \land \ to \neq \text{null} \ \land \ from \in Accounts \ \land \ to \in Accounts$$
  $$from \neq to$$
  $$amount > 0$$
  $$from.Balance \ge amount$$
* **Post ($Q$):**
  $$from.Balance' = from.Balance - amount$$
  $$to.Balance' = to.Balance + amount$$
  $$|Journal'| = |Journal| + 1 \ \land \ Journal'_{last} = \langle \text{now}, from.Number, to.Number, amount \rangle$$
  $$TotalBalance' = TotalBalance$$
* **Фрейм-условие (Side Effects):** Состояние счетов, отличных от $from$ и $to$, строго константно:
  $$\forall a \in Accounts \setminus \{from, to\}: a.Balance' = a.Balance$$

---

### 4.2. Операция 2: Пополнение счёта с лимитом (`Bank.Deposit`)

* **Сигнатура:** `DepositResult Deposit(DailyLimitAccount account, decimal amount)`
* **Инвариант сущности:** $0 \le DailyLimitRemaining \le SingleDepositLimit \times 100$

#### Формальная спецификация:
* **Pre ($P$):**
  $$account \neq \text{null} \ \land \ account \in Accounts$$
  $$amount > 0$$
  $$amount \le account.SingleDepositLimit$$
  $$amount \le account.DailyLimitRemaining$$
* **Post ($Q$):**
  $$account.Balance' = account.Balance + amount$$
  $$account.DailyLimitRemaining' = account.DailyLimitRemaining - amount$$
* **Фрейм-условие:** Балансы прочих участников системы не модифицируются.

---

### 4.3. Операция 3: Оплата услуг с комиссией (`Bank.PayService`)

* **Сигнатура:** `ServicePaymentResult PayService(Account account, string serviceName, decimal amount)`
* **Функция комиссии:** $Commission(s, a) = \text{round}(a \times Rate(s), 2)$

#### Формальная спецификация:
* **Pre ($P$):**
  $$account \neq \text{null} \ \land \ account \in Accounts$$
  $$serviceName \in \mathbf{dom}(ServiceCommissions)$$
  $$amount > 0$$
  $$account.Balance \ge amount + Commission(serviceName, amount)$$
* **Post ($Q$):**
  $$account.Balance' = account.Balance - (amount + Commission(serviceName, amount))$$
  $$\text{Status} = \text{Paid}$$

## 5. Мониторинг контрактов в графическом интерфейсе (GUI)

Для обеспечения наглядности принципов DbC в пользовательском интерфейсе реализованы:
1. **Реактивный двухфазный светофор:**
   - **Индикатор «Pre»:** Зеленый цвет сигнализирует о полном выполнении предусловий операции; красный — о нарушении хотя бы одного предикатного правила с детализацией ошибки в строке состояния.
   - **Индикатор «Post»:** Активируется после нажатия кнопки «Выполнить». Сигнализирует о выполнении гарантий метода (зеленый) либо о нарушении инвариантов системы (красный).
2. **Блокировка управляющих элементов:** Команда выполнения операции `ExecuteCommand` использует функциональный предикат `() => IsPreValid`, что предотвращает передачу заведомо невалидного контекста в слой бизнес-логики.
3. **Модальное окно спецификации («Показать контракт»):** Выводит математическую нотацию контракта, описание побочных эффектов и граничные примеры (позитивный/негативный сценарии) непосредственно пользователю системы.
